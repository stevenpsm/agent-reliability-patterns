# Agent 执行控制护栏

[English](execution-control-guardrails.en.md) | 简体中文

用途：按需复制到 system prompt、`AGENTS.md` 或任务执行契约。它补充通用的[长会话可靠性护栏](long-session-reliability-guardrails.md)，重点约束基线验证、重试、诊断、长期进程和时间预算。

## 1. 最小基线

- 自动化前，先用一条命令或最小脚本验证核心路径。
- 涉及转发、代理或流水线时，先写明 `source → bind → hop → target` 和每段成功判据。
- 基线不通过时，先修正方向、参数和前提，不增加 relay、重试或抽象层。
- 每增加一个组件，说明它解决的已验证约束；无法说明则不实现。

## 2. 重试门禁

- 每次重试前说明：什么条件发生了变化，或这次将获得什么新证据。
- 连续两次结果相同且无进展时转入诊断；禁止第四次无变化执行。
- 只有明确识别为瞬态错误时才自动重试，并设置退避、次数上限和总截止时间。
- 重试不得重置累计失败数和累计耗时。

## 3. 空输出与静默失败

- 空输出不是成功证据，也不是继续等待的充分理由。
- 空输出后检查返回码、stdout、stderr、异常 traceback、进程状态和已耗时。
- 禁止用不记录信息的宽泛异常处理继续循环。
- 长期运行任务必须保留可查询的日志、心跳或进度指标之一。

## 4. 进程生命周期

- 启动命令前将其分类为有限任务、长期驻留进程或事件驱动任务。
- 长期进程不得被当作预期自行退出的有限任务等待。
- 长期进程必须保留句柄或 PID，并具备就绪探测、错误收集、终止和清理机制。
- `start_new_session` 不表示非阻塞；`Popen` 也不表示可以放弃后续管理。

## 5. 时间预算

- 执行前计算最坏耗时：`尝试次数 × 单次 timeout + 退避 + 启动与清理开销`。
- 内部最坏耗时必须小于父级截止时间，并预留诊断和清理余量。
- timeout 表示超时后采取的失败动作，不代表后台任务已经正常启动。
- 实际耗时偏离预算时，停止增加等待并重新检查生命周期和阻塞点。

## 6. 汇报要求

- 区分 assistant 回合数、工具调用数和墙钟时间，不混为“尝试次数”。
- 报告当前假设、最小验证结果、重复次数、累计耗时和仍缺少的证据。
- 若方案因基础假设错误而废弃，主动报告废弃组件和影响，不以新增代码量表示进展。
